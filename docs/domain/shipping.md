# Basic shipping and order completion

Fulfillment owns a tenant-scoped Shipment. It references one or more sealed packages from one Sales Order and one fulfillment warehouse. The shipping address is copied from the Sales Order snapshot at creation. Carrier, service and tracking values are optional manual text; V1 has no carrier integration or label generation.

A Shipment moves `DRAFT → DISPATCHED` or `DRAFT → CANCELLED`. A cancelled draft releases its package assignments without changing stock. A dispatched Shipment is final. A partial shipment may contain a subset of a packed session's packages, and remaining sealed packages can be shipped later. If only part of an order was initially allocated, a later allocation can start another pick/pack cycle after the first cycle is packed; historical pick lists and packing sessions remain intact.

Dispatch is the physical outbound boundary. Fulfillment locks and validates its package assignments, derives exact variant/lot/serial/quantity/location dimensions from sealed package items, and calls the published Inventory dispatch operation in the same PostgreSQL transaction. Inventory posts one immutable `SHIPMENT_DISPATCH` movement with negative ledger entries at the packing location and a synchronous on-hand deduction. There is no fictitious external location. The Sales shipping projection advances only after this posting succeeds. Equal retry keys return the original dispatched Shipment; a key reused for another Shipment conflicts.

Sales lines expose ordered, allocated, picked, packed and shipped quantities. The order header exposes `NOT_SHIPPED`, `PARTIALLY_SHIPPED` or `SHIPPED`. When every line is fully shipped and no active reservation remains, Sales transitions the order to final `COMPLETED`. Normal cancellation is forbidden after any dispatch.

`SHP-YYYY-NNNNNN` is generated by a tenant/year counter. A database partial unique index prevents active or dispatched package assignment to two Shipments. Immutable package-content and completed-order guards protect historical evidence. Read, manage and dispatch permissions are separate; all queries are tenant-scoped. The HTTP contract is generated at `/v3/api-docs` for `/api/v1/shipments`.

Carrier APIs, rates, labels, tracking webhooks, proof of delivery, returns, reversals, customs and advanced split planning are deferred to V2.
